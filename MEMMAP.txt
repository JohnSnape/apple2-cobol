 128K Apple IIe, 65C02, ProDOS 8, 80-column.  "us" = our system.
 This file is the single authority on where things live.  Where a
 comment in a source file disagrees with it, this file is right and the
 comment is stale - say so and fix the comment.

 THE FOUR DECISIONS THIS MAP RESTS ON
  1. No graphics anywhere in this system, so all of low memory above
     the two text pages is ours.
  2. COBOL.SYSTEM loads at $2000 and STAYS there.  No relocation, no
     two-phase boot, no copy loop.
  3. The shared runtime is a FILE - COBOL.LIB, loaded to $3000 by
     every program that runs - not a block that tries to survive a
     QUIT.
  4. An overlay is a subroutine: JSR $8000, RTS back to the menu.
     ProDOS 8 has no QUIT-back-to-caller, so there is no chaining.

 Both text pages are driven by TEXTDRV; 80STORE is OFF system-wide.

------------------------------------------------------------------------
 THE PRODOS MEMORY BITMAP - why we ignore it
------------------------------------------------------------------------
 ProDOS tracks page usage at $BF58-$BF6F, and by default marks only
 pages $00, $01, $04-$07 and $BF as used - so pages $08-$1F, holding
 text page 2 and the data region, look free to it.

 We do not care, and it is worth knowing exactly why: ProDOS never
 chooses memory for us.  The MLI OPEN call takes the file buffer as a
 PARAMETER - we pass DA IOBUF ourselves - so there is no allocator to
 collide with.  The bitmap only matters when something else is doing
 the choosing: BASIC.SYSTEM, a program selector, or ALLOC_INTERRUPT.
 None of those are resident while a SYS program owns the machine.

 Startup USED TO claim $08-$1F anyway (three $FF stores at $BF59-$BF5B),
 on the grounds that six bytes to be honest about what we hold was worth
 it.  CLAIM WAS REMOVED 2026-08-16, because it is worse than
 unnecessary: ProDOS reads this map before it will write into a buffer
 handed to it, and a page marked in use comes back $56, BAD BUFFER
 ADDRESS.
   Found in WRITER, the word processor that shares this tree's screen
 driver and record layer: its GET_PREFIX buffer is at $1200 and the call
 failed every time until the claim went.  The same trap was set here -
 CATALOG reads the prefix into CATPATH at $0E00 - and CATALOG has never
 been run, so it was waiting rather than known.
   READ and WRITE are evidently not checked: EDIT's save streams through
 STAGE at $1C80, inside the old claimed range, and was verified
 byte-perfect on the machine.  It is the calls that hand ProDOS a buffer
 to FILL that check.

 The one exception is a test program BRUN from BASIC rather than run
 as a SYS file.  PG2TEST and AXTEST are both of those; they write over
 the Applesoft program area, which is harmless for a throwaway.

------------------------------------------------------------------------
 TWO WORLDS - the tools, and a running program
------------------------------------------------------------------------
 $0C00-$1FFF and $3000-$7FFF are IDENTICAL in both worlds: the data
 region and the library never move.  Only $2000 and $8000 upward
 differ, and you are never in both worlds at once.

 AT THE MENU (tools)               RUNNING A COMPILED PROGRAM
 $0C00-$1FFF data region           $0C00-$1FFF data region
 $2000-$2FFF COBOL.SYSTEM          $2000-$2FFF the launch stub
 $3000-$7FFF COBOL.LIB             $3000-$7FFF COBOL.LIB
 $8000-$AFFF overlay: FORMAT /     $8000-$91FF VM, the interpreter
             EDIT / QUERY /        $9200-$AFFF the object, then the
             REPORT / VM /                     data segment
             COMPILE1 / COMPILE2
 $B000-$BBFF three file buffers    $B000-$BBFF three file buffers
 $BC00-$BCFF two name buffers      $BC00-$BCFF two name buffers

 The interpreter is an OVERLAY like any other, so running a compiled
 program from the menu is a JSR that returns.  The standalone case
 differs only in who does the loading: the stub at $2000 BLOADs the
 library, the interpreter and the object to the same three addresses
 the menu would have used, then JSRs $8000.  One set of addresses in
 both worlds, which is what lets an object file contain no address of
 its own.

 A standalone compiled program is therefore one SYS file - a small
 stub followed by its p-code - plus two shared files on the disk:
 COBOL.LIB and the interpreter.  Nothing relocates and nothing is
 overwritten, because the interpreter deliberately does NOT live at
 $2000.

 If 8K for object plus data ever binds, the answer is not to shrink
 the interpreter.  In the standalone world there is no menu at $2000,
 so the interpreter moves down there and the whole band becomes the
 program's.  Same object file either way.

 THE SECOND PLACE TO GET ROOM, and it is bigger: the library is 9,768
 bytes of the 20K at $3000-$7FFF, so LIBEND sits around $562B and
 $5700-$7FFF is about ten and a half kilobytes of main memory that
 nothing uses.  Only the library's BASE is frozen, never its top - so
 that surplus is reclaimable without invalidating a single compiled
 object.  Between the two, a program can be given 22K contiguous
 before anything has to be paged from anywhere.

 WHAT NOT TO DO: page p-code in and out of a window from auxiliary
 memory.  It was considered and rejected, and the reasons are worth
 keeping because the idea is an attractive one.  A branch target is
 an offset from the code base, so every branch, GOTO, PERFORM and
 RET would need a which-page test; a PERFORM into another page swaps
 it in, and the RET swaps the first back, so a loop over a paragraph
 in a different page costs two AUXMOVEs an iteration - about 75ms
 for a 4K window, or 75 seconds over a thousand iterations.  That is
 not a corner case: PERFORM of a paragraph IS COBOL's control
 structure.  And the data segment, which is written constantly,
 would have nowhere to live.  Aux holds DATA, never code - decision
 7 - and the two wins above are free where this one is not.

 THE LIBRARY NEVER MOVES.  Compiled p-code calls the runtime by
 absolute address, so a floating base would mean BCDADD sat at $303C
 in one program and $083C in another, and an object would only run
 against the library it was compiled with.  The frozen table at $3000
 is what makes a compiler able to emit a call at all.
   When a program does not use text page 2, $0800-$0BFF is simply 1K
 of free DATA - a buffer the runtime may claim.  That recovers the
 memory without moving a single entry point.

------------------------------------------------------------------------
 LIBRARY BUDGET - $30C0-$7FFF is 20800 bytes
------------------------------------------------------------------------
 The first assembly of the library measured 5045 bytes for five
 modules in the old 4608-byte region at $0C00 - 437 bytes over, with
 seven modules still to write.  That is what forced this layout.

 Moving the code up to $3000 and leaving the data down at $0C00-$1FFF
 solves it outright:

   TEXTDRV   ~700     built        RECMAN    ~600    to write
   FILEIO    ~450     built        SCRSHOW   ~250    to move in
   CATALOG   ~700     built        SCRINP    ~600    to move in
   BCD      ~1500     built        CLASS     ~150    to write
   BANKS     ~350     built        DATIME    ~100    to write
   CONSOLE   ~500     built        ABORT     ~150    to write
   DSCREEN   ~350     built        PRINTER   ~350    to write
   AUXMEM    ~400     built                         ------
   NUMFMT    ~200     built        to come    ~2200
   PICTURE  ~1160     built
                     ------
   built    ~6310                  total     ~8510 of 20800

 Comfortable, with every planned module in.  The two-file split -
 COBOL.LIB plus a second COBOL.LI2 for programs that use the forms
 engine - is no longer needed and has been dropped.

 The buffers stopped counting entirely.  CATBLK's 512 bytes, BCD's
 144 bytes of digit arrays, CSHADOW's 1920, PICTURE's buffers - all
 addresses in the data region now, costing nothing on disk and nothing
 in the code budget.

 LIBEND at the foot of LIB.S is the real number.  Read it after every
 assembly; if it ever passes $8000 the library has collided with the
 overlay band.

------------------------------------------------------------------------
 WHY THE LIBRARY IS A FILE
------------------------------------------------------------------------
 Not because anything needs to survive a QUIT - once we QUIT, our
 system is on its way out and whatever the dispatcher clobbers on the
 way is no longer ours.  The library is a file because that is what
 makes a compiled program self-sufficient: it BLOADs COBOL.LIB to
 $3000 exactly as the menu did, and gets exactly the runtime the menu
 had, with no relinking and no copy of the library inside it.

 One binary on disk, one set of addresses.  The jump table at $3000 is
 the contract: a compiled object calls the runtime by address and
 outlives any particular assembly of the library, so entries are
 APPENDED and never reordered.

                      inline-string pointer; that routine is gone.
 $F0-$F3  Zone R      RNDSEED - 32-bit entropy counter, incremented
                      by every key-wait loop in the system, exactly
                      as the monitor's KEYIN ran RNDL/RNDH at
                      $4E/$4F.  Written ONLY by those loops; read by
                      anyone.  It is a seed, not a generator: it
                      stands still whenever nobody is waiting for a
                      key, so a PRNG must be seeded from it once and
                      then stepped on its own.
 $F4-$FF  reserved    future services

 GOLDEN RULE: a service routine touches only Zone S (+ its own Zone D
 slice), NEVER Zone P.  That lets the interpreter keep IP/SP/FP live
 across the many service calls one opcode makes.

 The library keeps ALL of its own state in the data region at $0CC0,
 not in zero page, precisely so it obeys this rule from the outside.

                        dictionaries, record buffers, symbol tables,
                        sort/query work, p-code program data.

                        HERE.
                        RECORDS GROW UP FROM $0C00; THE QUERY CURSOR
                        COMES DOWN FROM THE CEILING.  A cursor is
                        QMAX entries of QESZ bytes ending at $BF00,
                        so its base is $BF00 - QMAX*QESZ, and QRYINIT
                        refuses to start if that would land on the
                        records already in use.  On a plain 128K IIe
                        there is one bank and the two really do share
                        it.  This is a check, not an allocator - the
                        allocator is still owed.
 $BF00-$BFFF  reserved  top aux page - NOT available (upper bound is
                        $BEFF, not $BFFF).
 $C000-$CFFF  hardware  I/O (shared; not RAM)
 $D000-$FFFF  aux LC    aux language card, RAM bank 2 + $E000-$FFFF.
                        SINCE 2026-11-08: COBOL.AUX, library code that
                        RUNS here - BCD, PICTURE, ERRMSG (AUXLC.S),
                        $D000 up, ~4K used, must end below $FFFA.
                        Copied in at boot by LOADAUX (SYSLOAD.S).

 BANKS BEYOND THE FIRST
 A plain 128K IIe has one auxiliary bank.  A RamWorks-style card has
 up to 128, selected by writing the bank number to $C073.  FINDBNK
 counts them; AUXMEM turns a record number into a bank and an address.
 Every bank's usable space starts at $0C00, bank 0 included, so there
 is one mapping and no special case - we give up the 2,560 bytes below
 $0C00 in the upper banks to keep the arithmetic identical everywhere.

 The geometry is chosen so the division is a shift: records per bank
 is a power of two.  At 80 bytes a record, 512 records fill 40,960 of
 a bank's 45,824 - and a 16-bit record number at 512 records a bank
 reaches exactly 128 banks, so the two limits meet and neither wastes
 the other.

------------------------------------------------------------------------
 THE 80STORE DECISION - read this before touching a soft switch
------------------------------------------------------------------------
 80STORE is OFF for the life of the system.  This is the single fact
 that makes text page 2 reachable, and it changes what two switches
 mean:

   80STORE ON  (the old SCREEN.S, and the IIe firmware):
     $C054/$C055 select MAIN or AUX for the $0400-$07FF window.
     The display page is stuck on page 1 - the switch that would
     change it has been borrowed for banking.  This is why the IIe
     firmware only ever offered one 80-column page.

   80STORE OFF (TEXTDRV):
     $C054/$C055 are the DISPLAY PAGE select again - PG1SEL/PG2SEL.
     Banking moves to RAMRD/RAMWRT ($C002-$C005), which cover all of
     $0200-$BFFF, so they reach page 2 at $0800-$0BFF as easily as
     page 1.

 Consequences, all of them load-bearing:
   - Only TEXTDRV may touch $C002-$C005 or $C054/$C055.  MAINSW and
     AUXSW no longer exist as equates so that stale code fails to
     assemble instead of silently writing to the wrong bank - or
     worse, flipping the display page in the middle of a character.
   - Writes to aux are safe: RAMWRT does not affect instruction fetch,
     because fetches are reads.  Every routine banks aux in for one
     store and back out immediately.
   - READS from aux are the dangerous direction: RAMRD redirects
     instruction fetch too.  That is why the page mover exists at the
     same address in every bank, and why everything else uses AUXMOVE
     rather than raw RAMRD.
   - Zero page and the stack follow ALTZP, not RAMWRT, so they stay in
     main memory throughout.  That is why the driver can bank aux in
     and still use (SCRPTR),Y.
   - The monitor's COUT and GETLN are 40-column and page-1 only.  They
     are usable at startup, before the driver takes over.  After that,
     use PUTS and GETLN80.
   - AUXMOVE needs 80STORE off, which is now always true.  Code that
     used to turn it off and back on must no longer turn it back on.

------------------------------------------------------------------------
 CROSS-CUTTING NOTES
------------------------------------------------------------------------
 Cross-bank moves: firmware AUXMOVE $C311 shuttles data between main
   and aux over $0000-$BFFF (we use $0C00-$BEFF).  Params: $3C/$3D =
   src start, $3E/$3F = src END, inclusive - not a length;  $42/$43 =
   dst start.
   CARRY SET   = MAIN -> AUXILIARY
   CARRY CLEAR = AUXILIARY -> MAIN
   It reads the wrong way round and it fails quietly: the wrong carry
   moves the right number of bytes in the wrong direction, so a read
   leaves its buffer untouched and a write destroys the destination.
   AXTEST found this the hard way - every bank read back as zero.
   XFER $C314 is shelved (we run no code from aux).

 VERIFIED: selecting a RamWorks bank at $C073 and then calling AUXMOVE
   does reach that bank.  AXTEST wrote and read back all 128 banks on
   an 8MB card - every one distinct.  Brown's 1986 warning that AUXMOVE
   "does not work with the extra banks" means only that AUXMOVE has no
   bank parameter of its own, not that selection fails to compose with
   it.  That is what AUXMEM is built on.
   The first AXTEST run said otherwise only because the carry was
   backwards, so nothing was ever written.

 ProDOS globals we touch: MLI $BF00, system bitmap $BF58-$BF6F,
   DATE $BF90-$BF91, TIME $BF92-$BF93, MACHID $BF98.

 Program startup, every time:
   1. check for 128K (CHK128, from $0100) and a 65C02 (CHK65)
   2. BLOAD COBOL.LIB to $3000
   3. claim pages $08-$1F in the ProDOS bitmap
   4. JSR INIT80 ($3000)
   5. run
